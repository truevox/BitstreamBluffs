# Dual-proof public eligibility contract — draft v1 (#245)

**Not yet active or wired to public leaderboards.** This module is a pure, transport-independent decision library. It has no keys, server, wallet API, persistence, network or public publication. Offline/local modes remain playable and local ranking is untouched.

## Trust boundary

A result tagged `trusted` in JSON **is not itself authenticated**. No caller of this pure JS library can independently establish provenance by setting `kind`, `issuer`, `challengeId`, `digest` or `signature` fields. A future server must authenticate its own verifier execution, issued challenge (nonce, expiry, replay protection), entitlement/economy receipts, privacy consent, and audience eligibility **before** passing them as separate `simulation`, `authorization` and `consent` inputs. NEVER derive these from a client request or let a browser call alone award public ranks.

Client `request` cannot carry wallet balance, shard ownership, receipts, equipment grants, a trusted verdict, or a `verified` flag. A bundle hash is an integrity fingerprint only, not proof of ownership, humanity or real gameplay.

This module checks strict field sets, lane consistency, cross-input identity and matching replay outcome; it is not a verifier. Trusted infrastructure is currently unimplemented. All platform/network integration MUST remain disabled until separately authorized by the owner.

## Next

Explicit tests must exercise forged balances, missing tapes, mismatched builds, stale challenges, denials and unverified provisional publication. The score and rewards are never taken from a client-supplied wallet. ## Versioned request and response

API: `adjudicateDualProof({request,simulation,authorization,consent,allowProvisional})`. The public claim is the strict `bb-dual-proof` v1 object: `{format,version,runId,buildId,rulesetId,manifestDigest,tapeDigest,seed,biomeMask,lane,score,endTick,loadoutDigest,assistance,intent,challengeId}`. Digests use `sha256:<64 lowercase hex>`; score/end tick are safe nonnegative integers, lane is `stock`, `modded`, `official-daily` or `daily-draft`, and intent is `local`, `provisional-public` or `verified-public`. Unknown fields are rejected, including client wallet/balance, receipt, ranked/verified flags, auto-upload and claims to trusted execution. Strings and the shape are bounded; malformed requests cannot escape as exceptions.

The trusted simulation execution input has `{kind:'trusted-replay-execution',runId,buildId,verifierBuildId,verifiedCourse,score,endTick,tapeComplete,assistanceObserved,record}`. `record` MUST validate under existing `validateOutcomeRecord` and indicate a genuine `match`, not mere `consistent-with` or `inconclusive-legacy`. Its run/build/ruleset/manifest/tape/score/terminal tick must match the bounded request, while `verifiedCourse` (seed, biome mask, lane and loadout digest) MUST be derived from the replayed manifest by the authenticated verifier—not copied from a request, and a complete full tape is required. A claimed `human` lane with independently observed AI or tool assistance is invalid, not human-verified. The verifierBuildId is a separately sourced `sha256:` digest of the exact executable verifier, not the client build or a self-hash.

The trusted entitlement input has `{kind:'trusted-eligibility-receipt',status,runId,buildId,rulesetId,seed,biomeMask,lane,loadoutDigest,manifestDigest,challengeId,challengeStatus,economyStatus,equipmentStatus,modeStatus,pinnedVerifierBuildId}`. Every identity, including the exact manifest digest, must agree with the request and the executable verifier digest must agree with the trusted simulation report **even if entitlement is pending**, never only once both proofs become valid. Inconclusive replay reports must also bind their run/build/tape/manifest identity before allowing provisional treatment. `challengeStatus` is independently evaluated as `fresh`, `expired`, `reused` or `missing`; the function does not itself generate or time a nonce. `economyStatus`/`equipmentStatus` are `authorized`, `rejected` or `missing`. There is no client-controlled upgrade spending claim. A denial or stale challenge is invalid; incomplete receipt is unverified. A valid simulation and missing entitlement can never award a public ranking. A request for provisional-only publication cannot silently upgrade to verified-public, even if independent proof later becomes available; a new explicit user intent would be required.

The separate trusted privacy receipt has `{kind:'trusted-consent-receipt',status,runId,scope,audienceGate}`; `granted` consent and `passed` audience gate are both mandatory for any public publication. Local intent never publishes, even with complete proofs. Provisional publication is a **server-policy opt-in** (`allowProvisional:true`) and only for a public `provisional-public` request with successful consent/audience, absent/inconclusive proofs and **no invalid proof/eligibility**. It is explicitly labelled `UNVERIFIED`, and cannot award verified rank or public rewards.

A verdict object has fields `{format,version,proof,eligibility,competitiveness,privacy,provenance,publication,verifiedRankEligible,publicRewardEligible,provisionalLabel}`. Each status component is `{status:'valid'|'invalid'|'inconclusive'|'unverified',reason:<stable code>}`. Publication is `none`, `provisional-unverified` or `verified-eligible`. The provenance object contains the separately supplied verifier ID, pinned executable verifier digest, ruleset and consent scope when those receipts validate; these identifiers remain unauthenticated unless the future adapter enforces provenance externally. It never publishes a wallet balance, secret or user identity. The two booleans describe **eligibility only**, not actual publication/payment/ledger mutation. No route, price or verifier-service class influences the pure function: a free peer or paid hosted verifier sees the same canonical byte-level verdict for the same authenticated inputs. Four canonical SHA-256 fixtures are pinned in `tests/trust/dualProof.test.js` to detect future result drift.

## Security holes deliberately not claimed solved

This pure library does **NOT** authenticate an object labeled `trusted-*`, enforce rate/quotas, sign results, hold a nonce-reuse ledger, preserve keys, connect to a legitimate wallet, prove human motor actions, enforce account age, or grant rewards. Browser JavaScript can fabricate every fake input field. That cannot turn this helper into a trusted server; doing so would require a real independently authenticated adapter and external authorization. In particular, a local SHA-256 fingerprint/checksum is not a signature and recomputing it after tampering does not prove a real playthrough. The policy **MUST NOT** be wired into a public leaderboard or paid service until #244 and parent #135, the full input evidence storage/admission, the server authorizer, consent/audience policy and review are completed and approved.

No actual historical tape execution/compatibility is enabled before public release; the explicit `version` and pinned build/ruleset/verifier fields keep the eventual compatibility boundary clean. No changes to current local boards, save files, gameplay physics or player-facing menus.
