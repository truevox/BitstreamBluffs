## Why a new audit was needed

The existing busy-mix and song-coverage audits repeatedly poll an `AnalyserNode` in 2,048-frame windows on a 25 ms timer. That finds clipping in sampled regions but can miss transients between polls, especially at higher sample rates. They also cannot estimate reconstructed peaks between sample instants. Independent Astra/Codex review flagged these limitations as a separate release gate.

New QA code:
- `tools/music/qa-continuous-peak-worklet.mjs`: browser AudioWorklet processor, a **silent zero-output, parallel tap** on the unchanged real game's soft and final output nodes. The worklet consumes every supplied 128-frame render quantum, collects independent stereo sample peaks/RMS/nonfinite/ceiling violations, tracks expected-vs-observed frame positions, and optionally copies at most 3.5 seconds of stereo PCM into preallocated local typed arrays. It does **not** perform expensive reconstruction on the real-time thread, and it connects to the actual game destination only through a zero-gain QA sink.
- `tools/music/audit-continuous-output-peak.mjs`: operates solely from a *secure loopback* preview of the exact built game. Verifies **served HTML and JS bundle SHA-256 against this checkout's `dist/`**, starts One More Run by the existing browser gesture, enables vocals only in a disposable QA profile, attaches the taps, then checks four real songs in eight 2-second menu / heavy near-BSOD + wind + SFX windows. Separately verifies that crashing to menu preserves current song and clock and activates the Debumont lead; leaves production assets/settings untouched. The final-stage captured PCM is reconstructed **after the window**, on the browser main thread, with a 32-tap Blackman-windowed sinc at three fractional positions per sample (4× estimate). Records exact source and browser version, native sample rate and per-window drift/gaps.
- `tools/music/verify-continuous-peak-probe.mjs`: independent negative control using browser `OfflineAudioContext`. A known 0.95-amplitude sine on the left and 0.30 on the right produces 10,014 over-ceiling left-channel samples and zero on the right. The probe's own output is *exactly silent on both channels*. Full audio-render quanta can pad a partial last block to 44,160 worklet frames for a 44,100-frame offline buffer; this is expected WebAudio behavior.

## Important counterevidence and technical limits

Some **earlier exploratory pilots** using a much heavier 32-tap/4× *inside the audio thread* were associated with intermittent callback discontinuities (two to four reported gaps in one busy window) under concurrent CT223 load. The first design was abandoned. A subsequent 16-tap realtime estimator remained intermittently sensitive. The verified design moves all costly reconstruction off the real-time thread and explicitly persists render gap details (expected and actual `currentFrame`, missed/overlapped frame counts) **before throwing if gaps reappear**. A single passing run is not evidence there will never be dropouts under load, and the earlier failed pilots are not silently treated as passes.

**Neither the sample peak nor the 4× windowed-sinc reconstruction is a guarantee about every instant of all four complete songs.** Eight bounded 2-second windows cover only about 16.5 seconds of output across four songs. The reconstructed peak is an *approximation*, not a standards-certified true-peak measurement of the future output device, its resampler, or its DAC. The final hard sample ceiling can still generate nonlinear aliasing if forced to limit a severe high-frequency overload; it was not activated in representative busy-mix samples. Only Chromium/44.1 kHz was tested live; 44.1/48/96 kHz were covered separately by the existing source-bound synthetic `OfflineAudioContext` audit. Firefox and WebKit were not installed on CT223. CPU/thermal/audio driver behavior and Marvin's listening approval remain open.

## Reproduction (private QA only)

From a clean checkout containing commit `b84e67d` and these new tools, run `npm run build` then serve `dist/` on **localhost** (for example `python3 -m http.server 8224 --bind 127.0.0.1 --directory dist`). Browser AudioWorklet requires a secure context: the usual tailnet IP served over plain HTTP will not expose `AudioContext.audioWorklet`. Avoid relaxing Chrome security flags or moving the existing game service. Run `GAME_URL=http://127.0.0.1:8224/ node tools/music/verify-continuous-peak-probe.mjs`, then `GAME_URL=http://127.0.0.1:8224/ REPORT_OUT=/home/hermes/experiments/<unique-report-name>.json node tools/music/audit-continuous-output-peak.mjs`. The audit refuses to overwrite a previous report.
