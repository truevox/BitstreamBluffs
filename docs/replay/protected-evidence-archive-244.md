# Issue #244: protected LOCAL replay evidence — first implementation slice

**Status: library-only draft, not a completed issue or public service.** This is a local durable-reference registry over the existing `bitstream-replay-evidence` database, separate from the five visible Ghost Library roles. There is **no automatic upload**, leaderboard admission, player identification, analytics collection, wallet access or server request. A `submitted` reference is only a local role label: it does not submit anything.

## Architecture and constraints

- Existing `EvidenceStore` owns canonical `bb-replay-evidence` bundles with a full input tape, causal starting state, checkpoints, claims and manifest. It already stores these in a separate IndexedDB from `GhostLibrary`. Its `get()` rehashes stored bytes before returning them. The cosmetic trace and five displayed ghost roles can churn without modifying this authoritative evidence database.
- IndexedDB schema v2 adds `protectedRefs` alongside the preexisting `bundles` and `index` stores. Browser version upgrade retains v1 bundles and index, and creates the reference store only if missing. Existing v1 IndexedDB connections may block the upgrade until closed; the store reports memory-only fallback and protection fails instead of pretending to be durable.
- `protect(digest,{runId,role})` requires already-durable, hash-validated evidence; the local runId must agree with its stored local index, and seed/biome mask are extracted from the canonical manifest, never copied from request metadata. `role` is one of `candidate`, `submitted`, `pinned`. `protect()` is idempotent for the same run/course/role and digest; same role/different digest fails. An IndexedDB transaction checks the referenced index and writes a role atomically. Each evidence write and retry also checks the persisted run-ID binding inside its own read-write transaction, rather than trusting a stale tab cache. This is a local retention handle, not authenticated run identity.
- `listProtections()` returns local role entries, `protectedCount(digest)` is the count of separate roles, and `getProtected(key)` reads the persisted reference and its bytes together in a single transaction; if another tab has changed the role, it refuses as stale rather than returning the former bundle. `unprotect(key)` releases exactly one role atomically, rejecting stale-tab changes. It does **not** delete the evidence. `remove(digest)` refuses while any persisted reference exists, including references created in another tab after the current tab's cache loaded; a stale cached reference cannot indefinitely block deletion after another tab has unpinned it. It checks the persisted refs and deletes bundle/index in the same transaction, not in separate read/write steps. A failed delete does not purge the in-memory index.
- Quota, corruption and failed transactions are visible errors, not silent success. Memory-only or pending writes cannot acquire a durable protection role. These objects and their digests are *locally mutable by the device owner*; SHA-256 integrity alone does not authenticate who played or what upgrades they owned.
- Run IDs remain local handles, not trusted identity. The first slice currently binds one stored `runId` to each digest. Multiple genuinely separate run IDs sharing byte-identical evidence need an explicit many-run-to-one-bundle binding design **before** calling #244 complete.

## Measurements from actual recorded tapes (not an estimate of bundle size)

Measured on **nine existing SIM6 recorded `.tape.json` fixtures** under `tools/conformance/fixtures/cross-engine-sim6` (not synthetic tiny inputs). Uncompressed compact source tape JSON, **not** the final canonical `bb-replay-evidence` envelope, occupies **255,434 bytes in total**, with individual tapes from **5,703 bytes** (`collision-heavy`) to **86,627 bytes** (`bsod-pursuit-catch`); the median is **19,701 bytes**. Full-input row counts range **14–2,637**, and compact `{endTick,inputs}` portions occupy **169–24,783 bytes**. One unrelated legacy full `bb-replay-evidence` bundle fixture measures **2,494 bytes**. These are different layouts and must **not** be compared as full-bundle compression ratios. We have not measured a representative corpus of full current-production bundles or actual browser IndexedDB/quota pressure. That acceptance item stays open.

## Second independent review hardening

Two overlapping `put()` calls in one tab must not let an aborted write erase a successful cache entry. Durable writes take a *caller-supplied* run ID into their transaction and use the **persisted** row to resolve identity; stale cached run IDs cannot overrule another tab's explicit deletion/reassignment. On a conflicting pending write, the pending bytes remain explicitly memory-only and the retry loop continues to attempt unrelated pending bundles. A database `versionchange` closes and invalidates the handle, sets `backend=memory`, and reports an error; callers must reopen before any new protection can claim durability. These cases are covered by new multi-tab and lifecycle tests. No client UI or public claim is wired to this code.

## Third independent review and actual browser observations

A fresh exact-head code review also caught two stale-state mistakes: reopening the archive after browser-data deletion merged old references into the new database snapshot, and a failed duplicate write without a `runId` could erase the stored local run binding from the cache. Both are now covered by deterministic tests: reinit atomically replaces persisted index/protection snapshots, preserving *only* separately identified memory-only pending bytes; a failed duplicate write never overwrites an existing cached binding.

Real Chromium IndexedDB test command (local-only Vite dev server from this exact worktree; NO external network): `GAME_URL=http://127.0.0.1:18261/ node tools/replay/test-protected-evidence-browser.mjs`. The isolated browser suite passed **six** tests: cross-tab save/pin, restart/read/run-ID conflict, stale-role read refusal, protected deletion, explicit unpin/deletion after restart, and blocked v1→v2 upgrade with memory-only fallback plus later recovery. One real browser legacy `.bbreplay` bundle occupied **2,494 bytes**. This validates a legacy fixture and browser IDB transactions; it does **not** establish production-corpus storage pressure, all-browser compatibility, or physical Chromebook acceptance.

## Fourth independent review: pending writes and explicit deletion

The pending-bytes map now has a distinct `pendingMeta` map containing each failed write's **actual requested run ID**, independent of the current persisted index. This prevents a quota failure from dropping an explicitly requested run binding, and prevents reopening against another tab's conflicting persisted binding from silently claiming the pending bytes belong to that other run. The conflicting bytes remain visibly session-only with `durable=false`; other pending bundles continue flushing rather than being starved.

An explicit removal acquires an in-memory per-digest deletion marker **before** queueing its IndexedDB transaction. Retries skip marked digests, and any retry already queued necessarily precedes the transaction that removes it. Successful removal clears index, pending bytes and pending metadata only after the durable transaction completes; failed removal leaves them intact. Adversarial tests exercise failed binding, conflicting reinit, and overlapping successful write + pending deletion. No normal gameplay or server behavior changes.

## Fifth review: simultaneous writes, snapshot consistency, closed-database deletion

In-memory pending claims are retained when a different overlapping `put()` commits an unbound copy of the same digest. A pending claim is only cleared when the actual persisted run ID agrees. Both persisted indexes (`index`, `protectedRefs`) are now read through **one IndexedDB readonly transaction** on init/reopen, preventing mismatched cross-tab snapshots. Once the archive was ever opened as a durable IDB backend, an explicit deletion after `versionchange` must fail with `not-durable` until a new database connection succeeds; it never pretends removing a cached entry removed saved bytes. An instrumented, serializing IDB test fake provides a targeted failing-write race and transaction-scope verification.

A per-bundle `isBundleDurable(digest)` query now confirms the exact index and bundle bytes exist in one current IndexedDB readonly snapshot and match their SHA-256. This differs from the store-wide `durable` flag: another bundle's pending memory-only write does not make an already-durable import incorrectly appear session-only. The method returns false on unavailable/closed storage and when this digest itself remains pending; a checksum remains integrity only, not proof of legitimate play.

## Archive admission versus current ruleset verification

**Archive-only import** passes `archiveOnly:true` to the evidence store: it still checks exact SHA-256/canonical bundle structure, but it does not demand that the imported manifest's historical ruleset exists in the currently running game. It does not carry or invent an original local run ID. A conflicting pending local run-ID claim remains explicitly unresolved and cannot authorize a rank; independently persisted canonical bytes may still be retained as unverified archival evidence. Per-bundle durability reads the actual persisted index and bundle together, so it correctly reports existing bytes even when the same digest also has an unresolved memory-only run claim. This is preservation, not replay verification or equipment authorization.

Further exact-head reviewer corrections: pin-count receipts are computed within the same atomic transaction as the protected role write (a later count read cannot falsely report the completed pin as failed); failed durability reads handle request and transaction errors together; a successfully opened database handle is closed when subsequent index reads fail. These failures are injected in regression tests, and no external upload or browser telemetry is added.


## Forced IDB closure and historical pin review corrections

On unexpected browser `close` (without `versionchange`), the archive invalidates its connection and returns to memory-only status; the next explicit initialization may recover a real IDB backend. Reinitialization closes the previous connection rather than leaking handles. Historical, canonical evidence from a previously supported ruleset may be **pinned for local retention** after the current game resolver changes; this is structural SHA/canonical admission, never retrospective replay verification or reward authorization. Duplicate archive-only imports in memory fallback retain the original local run binding rather than overwriting it with an unbound index entry. Four regression tests exercise those independent-review findings.


## Automatic recovery and local-reference ABA protection

After a blocked v1→v2 upgrade clears, a successful `EvidenceStore.init()` now automatically retries session-only pending canonical bundles. Previously a newly open IDB connection could leave those captures stranded in memory until a *different run* was saved, risking loss on tab closure. Unresolved conflicts remain pending and visibly non-durable.

Every newly created protected local reference now carries a random 128-bit `generation` token from Web Crypto's `getRandomValues` (never a wall-clock value, never a player-authentication signature). Idempotent protection retains the existing generation; explicit unpin followed by re-pin assigns a NEW token, even for an identical run/digest/role key. Stale tabs compare generations before releasing or reading a protected reference and refuse the ABA race. This remains local storage lifecycle hygiene, not evidence of honest play.


An optional `runId` in `isBundleDurable(digest,{runId})` verifies the current **persisted** index binding and bundle SHA in one readonly transaction. This is necessary for Game Over to re-enable KEEP when a formerly quota-failed capture is later automatically flushed: a matching digest without the exact run ID is never enough to pin a player’s current run. The check remains local retention identity, not player authentication or competitive verification. A stale-tab deletion/reassignment negative case verifies it does not trust cached run identity.

## Exact-head review: stale cross-tab binding and cleared-browser import

`protect(digest,{runId})` no longer rejects because the current tab's in-memory index was loaded before another tab saved the bundle. The stored run ID and canonical bytes are read from one IndexedDB snapshot, and the role-commit transaction rechecks the persisted ID binding atomically. A separate negative test confirms the stale-tab cache cannot authorize a forged run ID. An archive-only import after this tab's prior durable DB was forcibly closed **never** inherits a stale run ID solely from the old cache; subsequent automatic flush keeps that import unbound. Finally, `unprotect(key,{expectedGeneration})` supports a UI-displayed generation snapshot so even a newer cache entry cannot silently redirect the user's Unpin intent to a replacement role created in another tab. These are local lifecycle protections, not public run verification.

## P1: never trust a caller's prevalidated digest

An independent review found a critical integrity shortcut in `EvidenceStore.put(bundle,meta,validated)`: a forged `{ok:true,bundleDigest:<existing pinned digest>}` hint could cause altered bytes to overwrite the original protected bundle under the pinned digest. **The shortcut is removed.** Every local write now independently parses the actual canonical bytes, validates the evidence grammar, calculates its SHA-256 digest, and rejects any supplied hint whose digest does not agree. All of this happens after the run-end frame, not inside simulation ticks. A new P1 regression reproduces both a flipped-byte forged hint and a valid but different canonical bundle with a forged old digest; in each case the existing pinned bytes, references and verified persisted run ID remain unchanged after restart. This is archival byte integrity, **not** public gameplay/score authentication.

## Independent follow-up: duplicate write resurrection, explicit Retry, single inspection

A duplicate update whose exact digest and run-ID binding were already persisted is checked before its write attempt. If that redundant update fails, it is reported to the caller but **is not added to automatic pending retries**, so an explicit deletion in another tab cannot be undone by a later store reopen. The local cache is never sufficient evidence for this classification: a persisted digest/run-ID probe is used. Conversely, a legitimately pending local write does not prohibit protecting a distinct already-durable persisted copy under its exact run binding. After an unexpected database close and site-data clear, the old cached index is not authoritative for accepting or rejecting an explicit new run ID.

`retryPending()` is a bounded, explicit local retry of session-only bytes after a quota or blocked-DB condition clears. `inspectBundle(digest,{runId})` verifies canonical bytes by digest from one IndexedDB transaction, returns independent `readable`, `durable`, and `runBound` flags, and uses verified session-only bytes only for export readiness. It does not perform public replay/score authentication. The Game Over Refresh path calls these APIs on explicit user action, avoiding three full SHA passes on every 16 MiB replay and enabling KEEP after a pending recording finally becomes durable.

## Exact-head review: atomic duplicate classification, cross-tab export and import status

A stale browser tab may have NO local index row even when another tab already saved the same digest/run. To keep a failed duplicate update from resurrecting data that another tab explicitly deleted, the durable write transaction itself now reads the existing index AND bundle, classifies previously durable exact bytes/run within that transaction, and records a receipt. A failed redundant write is reported but not queued for automatic replay; a genuinely novel failed write remains session-only pending. The classification is tied to the attempted write's atomic snapshot, not this tab's stale cache.

`get()/exportBundle()` now query and verify an actual persisted index+bundle snapshot even on a local cache miss. A replay first saved in a different tab can be inspected and exported here; an incomplete or corrupt stored record still fails closed. `inspectBundle(digest,{withProtections:true})` can atomically read index, canonical bytes and protected-reference count in ONE IndexedDB transaction, allowing import status to report a consistent durability/count snapshot rather than mixing two interleavable reads. Negative tests verify each behavior. This is only local byte-integrity and retention state, never gameplay authenticity.
