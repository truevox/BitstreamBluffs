# P0 #119 — Atomic local single-use suspend-slot foundation (2026-11-25)

**Inert infrastructure only; never a runtime savestate feature.** This small slice implements a device-local concurrency/persistence protocol *after* the production's pure V1 envelope parser and exact-build identity are already installed, but *before* any trusted serialized `RunScene`/Matter schema, recorder restore, user-facing UI or public eligibility admission. The original five-file implementation came from draft #379 atop earlier #370/#369, but this post-#56 v2.25.3 candidate is stacked on the v2.25.2 #56 Course Archive candidate, which itself tracks current `main` after #396. There is **no additional game physics, SIM revision, scoreboard, profile, loadout, reward, upload or user wallet change**.

## Owner policy and claims we explicitly do NOT make

- Owner decision 2026-11-22 in `docs/determinism/savestate-feasibility.md` section 11: a **single-use suspend** can remain official only if the complete genuine input tape from tick 0 is replayed for verification; the snapshot itself cannot prove score, legitimacy or producer identity. Repeatable Heavy Mode save/load is always tool-assisted and outside regular ranked boards.
- A `bb-savestate-cache` envelope's SHA-256 is **integrity/error detection**, NOT authentication; its parser returns `admission:'envelope-only'`. This module preserves that phrase. It never reports `restorable`, `trusted`, `ranked`, `eligible`, `verified`, or `resume succeeded`.
- The currently shipped game registers **no production savestate layout**. A caller must provide its *own trusted exact-build identity* and shipped registered schema validator; otherwise the `put` and `claim` methods fail closed. Test fixtures use a deliberately synthetic toy layout and cannot pass live restoration.
- Browser-storage copying to repeat a suspend is **not defeated** here; per owner, the later verifier must have independent complete replay evidence and may eventually record signed suspension events. This module does not build those services.

## Storage and concurrency contract

- One private IndexedDB `bb-single-use-suspend-v1` database/store holds at most one local serialized V1 envelope, bound to an exact build, physics ruleset, layout, run ID, tick and checksum. Max 16 MiB serialized bytes, with canonical parser limits enforced before any write. No last-known location, user identifier, file download or network upload.
- `put(bytes,expectedIdentity,registeredLayout)` makes a defensive byte copy, runs the existing strict exact-build envelope inspector and requires `purpose:'suspend'`. A stored record is still **only envelope-only admission**. By default an existing ready slot cannot be overwritten; explicit `replace:true` can replace only a *ready*, never a *claimed*, slot. A corrupted record with an unknown status is **not** silently replaced even with `replace:true`.
- `claim(identity,layout)` generates a cryptographically random UUID (fail closed without WebCrypto) and validates the exact same envelope **inside a single readwrite transaction**. Competing tabs serialize the read/claim; exactly one gets a token and a defensive byte copy. Others get `slot-claimed`. Build/physics/layout/schema/tick/digest mismatches leave bytes untouched and unclaimed.
- Only the holder may `consume(token)` after a *future* runtime has actually restored the entire world and recorder. It atomically deletes the slot. If a future runtime can certify an unchanged failed restore, only the holder may `release(token)` to make it available again. No automatic time-based leases: if the tab dies midclaim, the slot stays held rather than silently enabling a double resume. Explicit `clearReady()` never steals a claimed slot.
- A failed IDB transaction, quota, missing IndexedDB or unsecure token returns a distinct failure; the layer never advertises persistence before `tx.oncomplete`. No cache, derived GBrain or server side state is manipulated.
